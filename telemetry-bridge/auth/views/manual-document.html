1. System overview

The ESP32-S3 is the I²C controller for three followers on one bus (400 kHz, SCL GPIO40 / SDA GPIO41):

DeviceAddressRole
INA2260x40PV (solar) bus voltage, current, power, shunt
BQ769420x08Battery monitor: cell voltages, pack voltage, temperature, FET control
BQ257980x6BMPPT charger: ACDRV power-path selection, ADCs, fault flags

Data path: ESP32-S3 → Wi-Fi → UDP port 3333 → telemetry bridge (Node.js, 127.0.0.1:8080) → Apache /telemetry/ → browser (Server-Sent Events). Commands travel the other way: browser or Windows tool → POST /telemetry/command → bridge → UDP JSON to the ESP32 → debug_result reply.

Main navigation: Home · Dashboard · Sign in / username. Dashboard sections: I²C Telemetry · Network Statistics · Logged Telemetry · Digital Twin; operators also have Programming · Branch Definition · Manual.

2. Signing in and roles

The dashboard and saved recordings require a viewer or operator session; programming, branch definitions, and manual controls require an operator account. Click Sign in (top right), enter your username and password, and use ← Back to return.

AccountRead telemetry / historyStart or stop recordingsSend hardware commands
ViewerYesNoNo
OperatorYesYesYes, plus the separate command token
  • The session is an HttpOnly, SameSite=Strict cookie. Viewer sessions expire after inactivity (default 15 min, AUTH_SESSION_SECONDS 60–86400).
  • Only one operator holds control at a time. The site renews the control lease every 15 s while visible; the lease defaults to 45 s (AUTH_OPERATOR_LEASE_SECONDS, 30–300). A second operator gets HTTP 409 until the lease lapses or the first signs out.
  • Hardware commands always also need the command token (X-Command-Token). Enter it in the token field of the Programming or Branch Definition page; it is not saved.
  • A bridge restart invalidates all sessions; sign in again.

4. I²C Telemetry

An interactive bus view. The Peripherals bank at the top holds page tiles (Overview, ESP32-S3 controller, Light + temperature ADC peripheral). The SDA (red) and SCL (green) lines connect the controller to follower tiles for INA226, BQ25798 and BQ76942.

  • Open a tile to see that device's decoded values in a detail window; the bus view stays visible.
  • ESP32 status (top left of the Peripherals bank) shows whether recent telemetry is reaching the browser through the bridge. It does not test each I²C device.
  • Each follower tile shows an ACK indicator and latest values; “no data” means no valid packet for that device yet.
  • Mock Telemetry toggle (top right) shows locally generated demonstration values. Turn it off to see packets from the ESP32. The page never starts mock data while the bridge reports live telemetry.
  • A Streaming Telemetry card sits at the bottom of this page with the same On/Off toggle and live cards (including the ADC devices card) as the Programming page. The setting is shared: turning it on here or on Programming makes this page subscribe to the shared stream, show live cards below the bus view, hides tiles of devices that are not present, and shows a STREAMING badge in the nav.

5. Network Statistics

Header: Telemetry Network Statistics. It measures the Wi-Fi/UDP link from packet sequence numbers and bridge receive times.

Source card

Event stream (/telemetry/events), Health URL (/telemetry/health), nominal packet period (default 1000 ms) and window (1, 5, 15 or 60 min). Click Connect; Clear stats resets counters.

Tiles

TileMeaning
Link stateConnected, Stale, Offline or Bridge unreachable
Last packet ageTime since the last packet and the stale threshold
ESP32 endpointSource IP:port of the board, with port-change and reboot counts
Signal (RSSI)Only with v5/v6 packets (debug mode); otherwise n/a
Pending commands / Command controlCommands waiting for a device reply; whether the bridge is ready and the token is accepted

Charts and table

Packet inter-arrival, RFC 3550 jitter, loss % per bucket, gaps/duplicates/out-of-order, command RTT and RSSI, plus a window statistics table.

How the numbers are computed. Loss counts gaps in the 16-bit sequence (which skips 0). A backward jump greater than 64 or a forward jump of 1000 or more is treated as a reboot, not loss. Jitter is measured against the nominal period because v4 packets carry no transmit timestamp.

6. Programming

Register-level I²C access over the Wi-Fi bridge (formerly “Debug Mode”).

Bridge card

Event stream, Health and Command URLs (defaults under /telemetry/) and the Command Token. Click Connect. The Token pill shows whether the bridge accepted the token.

Debug control

  • Enable Debug / Disable Debug sends debug_control. Debug mode is off at boot.
  • Scan Period 200–5000 ms → Apply (set_scan_period; the firmware also clamps to this range).
  • Bus Scan + Probe scans 0x08–0x77 and re-probes presence. Results appear in the Bus Scan panel.
  • Presence tiles show each device as present, absent, NACK, timeout, paused or error (from v5/v6 packets).

Streaming Telemetry

Toggle On to show live cards for present devices only, with sparklines (1/5/15/60 min), last-update age and LIVE/STALE indicators. Absent or not-polled devices appear as small chips. The setting is remembered in the browser and also switches I²C Telemetry to the shared stream (its Streaming Telemetry card is at the bottom of that page).

Register Access

Pick a Device and Register, or add a register address. Reads show raw bytes and converted engineering values using the register map shared with the Windows tool. Writes are limited to approved registers.

Sequence Runner

One command per line. Accepted syntax:

debug on
period 500
scan
read 0x40 0xFE
read 0x08 0x14
write 0x40 0x05 0x0A 0x00
delay 200
i2cget -c 0x40 -r 0x05 -l 2

“stop on error” halts at the first failure. A session log can be downloaded as .txt.

7. Logged Telemetry

Records real UDP telemetry to the bridge's private SQLite database and lets you replay and export it.

  • Capture Control: enter a Run Name and click Start Recording (operator only). A recording begins with the latest fresh hardware packet and continues without a browser open. Stop Recording ends it.
  • Saved runs: the library on the left; refresh with the circular-arrow button.
  • Graph: pick a metric. Click a bucket or use arrow keys to select it; the data table then shows packets in that bucket. Double-click the selection label to clear it.
  • Recorded data tables (Packets and others) and Export current CSV for the current graph interval.
  • Branch Definition executions are also listed here with their full event timeline.

Automatic run boundaries

  • Outside debug mode, a confirmed power-source change (BQ25798 REG13 ACDRV1 = PV ↔ ACDRV2/off = BAT/secondary) ends the run and starts the next.
  • Entering debug keeps the run and tags later samples as Debug; leaving debug ends the run.
  • A confirmed device reboot ends the run with device_reboot and starts a linked successor.
  • Missing or contradictory MPPT evidence is “unknown” and never creates a boundary.

8. Branch Definition

A block editor (formerly “Visual Codes”) for ordered steps and branch paths. The bridge executes saved definitions; the browser does not schedule commands.

Blocks

BlockWhat it does
CommandLED, Debug mode, Sensor polling, MPPT ACDRV, I²C read/write, Scan period, I²C scan, I²C probe
Register readReads a supported register (1 or 2 bytes). Its value can feed a later If / Else or Wait.
Register writeWrites an approved register: BQ76942 0x3E; BQ25798 0x0F 0x10 0x12 0x13 0x14 0x2E 0x30; INA226 0x00 0x05 0x06 0x07
Delay1–600000 ms
Wait for valueWaits until a condition is TRUE, with a timeout (1–600000 ms)
IF / ELSEEvaluates a condition once and runs the TRUE or FALSE path

Editing

  • Drag a block from Blocks to an insertion point in Code path, or click Add. To add inside an IF / ELSE, first select its TRUE or FALSE path.
  • Validation issues are listed under the canvas; the definition must be valid to save.
  • Use Saved Branch Definitions → Load, plus New, Duplicate and Save. Saving needs the current revision, so concurrent edits do not overwrite each other.
  • Limits: 200 blocks, nesting depth 8, no loops, no automatic retries.

Execution

  • Simulate runs against the optional JSON in the Execution box and sends no hardware commands. Shape: {"telemetry":{…},"raw":{…},"registers":{"0x40:0x00":16679}}. registers supplies values for Register read blocks and register conditions during simulation.
  • Review live execution → Confirm live execution. This needs an operator session, the command token, fresh UDP telemetry and an idle recorder. Live commands are dispatched at most once per second. A live run also creates a linked Logged Telemetry run.
  • Pause (expires after 60 s), Resume (needs the token) and Stop. Runs are capped at 30 minutes.
  • After an unknown command outcome (timeout) or a bridge restart, live commands are blocked until you inspect the device, tick “I reviewed the device state” and click Acknowledge review.

9. If / Else on block results

An IF / ELSE (or Wait for value) condition can compare the result of an earlier Register read block.

  1. Add a Register read block, for example INA226 0x40 register 0x00 (2 bytes).
  2. Below it, add an IF / ELSE block.
  3. In the condition, set the left operand to Block result and choose that read (listed as Block N · device register).
  4. Choose an operator and set the right operand to Value in Hex format.
  5. Put blocks into the TRUE and FALSE paths. Both paths must contain at least one block.
OperatorTRUE when
== != < <= > >=Numeric comparison of the decoded register value
& (bit mask)(value AND mask) ≠ 0: any masked bit is set. Hex operands only.
AND / OR / NOTCombine 2–8 comparisons. Unknown values stay unknown under NOT and cannot select a branch.
  • The value is the read's bytes combined using the register's byte order (BQ76942 little-endian; INA226 and BQ25798 big-endian). This is the raw register integer, not an engineering unit.
  • The referenced read must come earlier on the same path. A read inside another IF's branch is not visible after that IF, because it might not have run.
  • If the read produced no value, the condition is unknown and the IF fails after its 30 s evaluation window rather than guessing a branch.
  • Each read records a register_value event, and each branch records a branch event with the compared values. Both are visible in run history.
Register read   INA226 (0x40) 0x00, 2 bytes
IF  Block result [Block 1]  &  0x8000
  TRUE  → Command: LED On
  FALSE → Register write INA226 0x00 ...
Evaluation happens in the telemetry bridge, which reuses the device reply to the i2c_read command. No firmware change or reflash is needed.

Adding your own registers to a condition

A condition can also read a register directly, including one that is not in the built-in catalog, without a separate Register read block.

  1. Set an operand to Register and click Add register.
  2. Enter the device address in hex (7-bit, 0x08–0x77), the register in hex (0x00–0xFF), the width (1 or 2 bytes), the byte order for 2-byte reads, and an optional name.
  3. Click Add. The register is selected in that operand and appears under Added registers in every register picker.
  4. Set the other operand to a Hex value and choose an operator as above.
  • Added registers are saved in the Branch Definition (its registers list), so they come back when you load it. They are also remembered in this browser, so they are offered in new Branch Definitions too; choosing one copies it into the current definition.
  • During a live run the bridge sends an i2c_read for each added register when the condition is evaluated (at most once per second while it waits), exactly like a Register read block, then compares the decoded value.
  • In simulation, supply the value under the register's id or "<addr>:<reg>", for example {"0x48:0x00": 25}.
  • Reading some registers has side effects (for example clear-on-read status flags). Only add registers whose datasheet says a read is safe.

12. Firmware link behavior

  • Stop-and-wait: after each telemetry packet the firmware waits for the bridge ACK. The wait is min(250 ms, scan period / 4): 250 ms at the default 1000 ms period and 50 ms at 200 ms.
  • Scan period defaults to 1000 ms and can be set to 200–5000 ms.
  • Presence detection: devices are probed at startup, every 5000 ms and on demand. Absent devices are skipped, so they cost no 100 ms transaction timeouts.
  • Commands are JSON over UDP and are handled as soon as they arrive. Each returns debug_result. The bridge waits up to COMMAND_TIMEOUT_MS (default 4000 ms) for the reply; a timeout means the outcome is unknown.
  • Wi-Fi: reconnects use exponential backoff from 1 s to 30 s, forever. Debug mode turns modem sleep off (WIFI_PS_NONE, lower latency, higher current); debug off restores WIFI_PS_MIN_MODEM.
Debug mode is required for BMS pack voltage, BMS temperature, the BQ25798 ADCs (IBUS, VBUS, VAC1, VBAT, VSYS, TDIE) and the ADC temperature device. These values are only in v6 packets, which are sent only while debug mode is on.

13. Packet versions v4 / v5 / v6

VersionWhen sentContent
v4 (0x0004)Debug off20 words: PV, BMS cells, MPPT REG13/fault, polled-sensor mask (word 15), light peripheral (words 18–19). No transmit timestamp.
v5 (0x0005)Debug on (link-stats/debug builds)v4 plus 16 words: RSSI, uptime, UDP tx errors, ACK timeouts, Wi-Fi reconnects, flags, present/probed masks, scan/probe period, per-device error counts and status, I²C bus time, last ACK RTT.
v6 (0x0006)Debug on (current firmware)v5 words plus 12 Streaming Telemetry words (36–47): validity flags, BQ76942 PACK 0x36 and temperature 0x68, BQ25798 IBUS/VBUS/VAC1/VBAT/VSYS/TDIE ADCs, REG2E readback, ADC TEMP_OUT mV and GPIO assignment.

Device status codes (v5/v6): 0 ok, 1 absent, 2 NACK, 3 timeout, 4 paused, 5 error, F unknown. In v6, the fourth cell slot is physical cell 4; older formats used cell 10.

14. Bridge and deployment

  • The bridge (telemetry-bridge/server.js) listens on UDP 3333 and HTTP 127.0.0.1:8080, behind Apache at /telemetry/. It runs as the systemd service cubesat-telemetry.
  • Key routes: /events (SSE), /health, /healthz (readiness only), /command (?wait=1 for a synchronous result), /runs, /sequences, /sequence-executions, /auth/*, /aps/model, /aps/token.
  • Secrets (command token, JWT account file, APS client ID/secret) live only in root-owned chmod 600 environment files on the server, never in the repository or the site.
  • Site deploy: upload the full site/ folder to the Apache document root. Asset URLs carry cache tags (?v=YYYYMMDDx); bump them when files change.
  • Bridge deploy: copy telemetry-bridge/, run npm ci, restart cubesat-telemetry and check /healthz. Set DEPLOYED_REVISION so recordings are labeled with the decoder version. scripts/backup-live.sh, deploy-live.sh and rollback-live.sh automate this.
  • If the site sends a Content Security Policy, allow developer.api.autodesk.com and cdn.derivative.autodesk.com, plus worker-src blob:, for the Digital Twin.

16. Reference tables

Register conversions (value = raw × scale + offset)

  • BQ76942 (16-bit little-endian): cells 0x14/16/18/1A in mV; PACK 0x36 in 10 mV; CC2 0x3A signed mA; temperature 0x68 in 0.1 K − 273.15; 0x3E is the subcommand address.
  • BQ25798 (16-bit ADC big-endian): IBUS 0x31 and IBAT 0x33 signed 1 mA; VBUS 0x35, VAC1 0x37, VAC2 0x39, VBAT 0x3B, VSYS 0x3D in 1 mV; TDIE 0x41 signed 0.5 °C.
  • INA226 (big-endian): shunt 2.5 µV, bus 1.25 mV; current and power assume current_LSB = 1 mA.

Readable registers for Register read blocks

  • BMS 0x08 (2 bytes): 0x14 0x16 0x18 0x1A 0x36 0x3A 0x68 0x3E
  • MPPT 0x6B (1 byte): 0x0F 0x10 0x12 0x13 0x14 0x1B 0x1C 0x1E 0x2E 0x30 0x48; (2 bytes): 0x31 0x33 0x35 0x37 0x39 0x3B 0x3D 0x41
  • PV 0x40 (2 bytes): 0x00–0x07, 0xFE, 0xFF
