# Backend sequence execution (Batch 5B)

Sequences are version 1 JSON definitions with ordered `steps`. Supported blocks are `command`, `registerRead`, `registerWrite`, `delay`, `waitUntil`, `runSaved`, `message`, and `if` with `then` and optional `else` arrays. An empty remaining step list terminates successfully. Conditions use `==`, `!=`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, and `NOT`. A metric operand is `{ "metric": "pv.busVoltageV" }`; a constant is `{ "constant": 5, "unit": "V" }`. Unknown telemetry stays unknown under `NOT` and cannot select a branch.

`POST /sequences` saves a definition; `PUT /sequences/:id` requires the current `revision` and matching `confirmed_revision` after explicit operator confirmation. `POST /sequences/:id/preflight` returns a 30-second confirmation token for a specific operator, revision, and device. `POST /sequences/:id/execute` accepts `{ "mode": "live", "confirmation_token": "..." }` or `{ "mode": "simulation", "telemetry": { ... } }`. Execution status and ordered events are available under `/sequence-executions` and `/sequence-executions/:id/events?after=0`. Active operator controls are `pause`, `resume`, and `stop` POST subroutes. Live start and resume require the command token as well as the authenticated operator session and CSRF header.

Live execution uses one server process and one active sequence lock. It requires fresh UDP telemetry from the pinned device and endpoint, a healthy recorder, and continuous operator lease ownership. Manual commands remain serialized against live sequence control. A branch attaches transactionally to an active recording for the same device and source address. It cannot stop or reset that recording on completion or failure. A branch started independently still creates and closes its own recording session; duplicate recording starts are rejected. Operators can stop a shared recording explicitly, while a sequence-owned recording remains protected until execution ends. The engine does not renew the operator lease; if browser heartbeats stop, the lease expires and execution fails. A pause waits for any transmitted command response, and time spent paused counts against the 30-minute run deadline. Pause expires after 60 seconds. Blocks are limited to 200, nesting to 8, delay and condition waits to 10 minutes, and live command dispatch to at most once per second. There are no loops or automatic retries.

The safe state after a failure is **no further command dispatch**. No electrical rollback or shutdown command is inferred. A matching ESP32 response reports the device operation result; a write acknowledgment does not verify the register's later value. A command timeout has an unknown hardware outcome. The bridge blocks further live sequences and writes until the active operator reviews the device and calls `/sequence-executions/:id/recover`. Interrupted live executions also require recovery after restart. Simulation never uses the UDP command transport or hardware recording.

Sequence definitions, immutable execution snapshots, and ordered events are stored in the existing private recording database. Live execution joins the current run or creates one if none is active. The execution stores both its initial recording run ID and recording session ID, which can span the existing telemetry-driven run segments. Branch state, comparison, command, and step events also appear as existing `sequence_step` events in the current session timeline; simulation never annotates hardware recordings. The browser is not involved in scheduling. `/events` emits sequence events and active status; clients should reload the execution and paginated events after reconnecting.

## Run history (Batch 5D)

Every execution creates a durable sequence run before its first block. The execution stores the exact definition revision, mode, operator, start and end times, final state, completed step count, and a direct telemetry run ID for live mode. Simulations remain in sequence history without creating a hardware telemetry recording. The Runs and Sequences pages show the saved execution timeline to operators without rerunning it. Viewer run timelines retain recorded branch annotations, while sequence definitions and their APIs remain operator-only. Step events include bounded telemetry snapshots; condition and branch events preserve comparison operands, evaluated values, packet sequence, and receive time. Command results and errors retain acknowledgment evidence and failure explanations.

`POST /sequences/:id/execute` accepts an optional client-generated UUID `execution_id`. Repeating the same request ID for the same operator, definition revision, and mode returns its existing execution instead of dispatching again. A bridge restart closes any unfinished execution as failed with `bridge_restart` and appends one recovery event. An interrupted live execution still requires device review before another write.

## Block-result operands and bit masks (Branch Definition)

A condition operand may be `{ "step": "<registerRead block id>" }`. It evaluates to the integer value that block read in the current execution, decoded with the register's byte order, and has type `hex`. The block must be a `registerRead` (or `i2c_read` command) that appears earlier on the same path; reads inside a sibling IF branch are not visible after that IF. Validation rejects other references. The comparison operator `&` (hex only) is TRUE when `(left & right) != 0`. Each read records a `register_value` event. In simulation, read values come from `telemetry.registers` keyed `"<addr>:<reg>"` (for example `{"0x40:0x00": 16679}`). No firmware change is required: the bridge reuses the `i2c_read` reply.

## User-added condition registers

A sequence may carry an optional top-level `registers` array (max 32) of registers added from the editor's condition picker:

```json
"registers": [{ "id": "user-48-00-2", "label": "Temp sensor", "addr": "0x48", "reg": "0x00", "len": 2, "endian": "big" }]
```

`id` is `user-<addr>-<reg>-<len>` (hex without `0x`). `addr` must be a 7-bit address `0x08`–`0x77`, `reg` `0x00`–`0xFF`, `len` 1 or 2, `endian` `big` or `little`, and `label` is optional (≤60 chars). Duplicate ids or duplicate addr/reg/len targets are rejected. A condition operand `{ "register": "user-48-00-2" }` has type `hex`. In live runs the engine issues an `i2c_read` for each referenced added register at condition-evaluation time (same paced path and events as catalog register operands: `command_intent`, `command_result`, and `command_error` on failure) and decodes it with the given byte order. In simulation the value comes from `telemetry.packet.register_values` keyed by the id or by `"<addr>:<reg>"`. Added registers are also available to read blocks; their width and byte order come from the definition snapshot. The firmware's supported-device validation still applies.

## Shared operator register registry

`GET /registers` lists custom metadata. `POST /registers` accepts `{addr, reg, len, endian, label?}` (an existing `id` is accepted but canonicalized). Both routes require a signed-in operator. Additions require the same-origin CSRF header, but do not claim the hardware control lease or require the command token. Metadata persists in the private recording database's `register_registry` table; no new production configuration is required. Without configured recording storage the endpoint returns 503.

One shared entry is allowed per device/register target (up to 1024 custom targets). Atomic additions merge distinct targets; identical retries return the existing entry. Different widths, byte orders, or nonempty custom labels for the same target return 409. Built-in targets return their canonical catalog entry and cannot be overridden by a custom width or byte order. Shared additions are read-only metadata: command writes retain the independent backend allowlist, exact-width validation, reserved-bit restrictions, command token, CSRF and active operator lease.

Debug Mode, Branch Definition read/command blocks and condition operands, and manual command suggestions use the registry. Mounted clients poll every two seconds; a browser channel accelerates same-browser updates, and focus refresh handles suspended tabs. These updates only replace options, never the definition or unfinished text fields. Unsaved definitions also remain in memory across navigation and clear on sign-out. A reload requires saving the definition first; registry metadata itself survives reload and bridge restart. Existing schemaVersion 1 definitions, telemetry operand IDs, user IDs and embedded metadata remain compatible. Definitions keep their own metadata snapshots even if a registry entry differs.

The legacy browser list (`cubesat.sequence.registers.v1`) migrates to the bridge when register controls mount. Entries that fail migration remain in browser storage. Loading a definition also offers its added metadata to the registry without rewriting the saved definition.

MPPT `0x2F` is ADC Function Disable 0, and `0x30` is ADC Function Disable 1, each one byte. TI SLUSDV2C sections 7.5.1.43–44 document hardware R/W access and reserved fields. Project policy continues to allow writes only to `0x30`; `0x2F` is exposed read-only. Neither has a value in the periodic telemetry protocol, so the overview shows metadata only. Source: https://www.ti.com/lit/ds/symlink/bq25798.pdf .

## Saved sequence composition and messages

A `runSaved` block has `{ "id": "call", "type": "runSaved", "sequenceId": "saved-id", "revision": 1 }`. It may appear on any path. References pin immutable revisions, stored in `sequence_revisions`; existing current definitions are backfilled on startup. A save validates all references, including unselected conditional paths. Direct or indirect references back to the same definition ID, missing revisions, combined IF/call nesting beyond 8, more than 1000 expanded blocks, and dependency snapshots over 1 MiB are rejected. Each individual definition retains its 200-block and 64 KiB limits. Revision numbers never repeat after deletion and recreation.

Preflight and execution validate every pinned definition against current command safety policy. The execution's `definition.dependencies` contains every referenced definition revision, so editing or deleting the library later cannot change a run's evidence. Calls execute in the parent engine with the same operator, target, mode, pacing, pause/cancel, duration deadline, recording and unknown-outcome lock. Register metadata and block read results have a separate scope per call. Nested start/completion/failure events and every block's definition ID, revision and invocation/conditional `path` distinguish repeated calls and duplicate block IDs across definitions.

A `message` block has `{ "id": "note", "type": "message", "message": "Operator note" }`. Its nonblank plain text is limited to 1000 UTF-16 code units; control characters other than tab/newline/CR are rejected. Nothing is evaluated or formatted as a command. Only executing the block records a timestamped `message` event with block and path identity. Live events also annotate the linked telemetry recording; simulations remain isolated. The editor, Defined Runs history and recording timelines render messages as escaped text.

`DELETE /sequences/:id` requires `{ "revision": 1, "confirmed_revision": 1 }`, operator authentication and same-origin CSRF protection. Definition maintenance, including deletion, does not require the hardware lease. The worker checks the current revision and dependency guards in the same transaction as deletion. Any current saved definition referencing the target, directly or transitively through pinned historical revisions, blocks deletion. Immutable revisions and execution snapshots remain available. PUT also uses transactional revision comparison; neither a stale delete nor a stale confirmed overwrite can change storage.

The editor confirms the definition ID/revision and consequences before overwrite or deletion. Cancel sends no destructive request and leaves edits intact; conflict Cancel never reloads. New, Load, navigation and browser exit guard unsaved changes, while clean definitions do not prompt. In-app navigation retains the in-memory draft; sign-out clears it. Successful deletion of the loaded definition retains its editor contents as an unsaved copy.
