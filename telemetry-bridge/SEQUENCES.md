# Backend sequence execution (Batch 5B)

Sequences are version 1 JSON definitions with ordered `steps`. Supported blocks are `command`, `registerRead`, `registerWrite`, `delay`, `waitUntil`, and `if` with `then` and optional `else` arrays. An empty remaining step list terminates successfully. Conditions use `==`, `!=`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, and `NOT`. A metric operand is `{ "metric": "pv.busVoltageV" }`; a constant is `{ "constant": 5, "unit": "V" }`. Unknown telemetry stays unknown under `NOT` and cannot select a branch.

`POST /sequences` saves a definition; `PUT /sequences/:id` requires the current `revision`. `POST /sequences/:id/preflight` returns a 30-second confirmation token for a specific operator, revision, and device. `POST /sequences/:id/execute` accepts `{ "mode": "live", "confirmation_token": "..." }` or `{ "mode": "simulation", "telemetry": { ... } }`. Execution status and ordered events are available under `/sequence-executions` and `/sequence-executions/:id/events?after=0`. Active operator controls are `pause`, `resume`, and `stop` POST subroutes. Live start and resume require the command token as well as the authenticated operator session and CSRF header.

Live execution uses one server process and one active sequence lock. It requires fresh UDP telemetry from the pinned device and endpoint, an idle recorder, and continuous operator lease ownership. Manual commands and independent recording changes are rejected while a live sequence owns them. The engine does not renew the operator lease; if browser heartbeats stop, the lease expires and execution fails. A pause waits for any transmitted command response, and time spent paused counts against the 30-minute run deadline. Pause expires after 60 seconds. Blocks are limited to 200, nesting to 8, delay and condition waits to 10 minutes, and live command dispatch to at most once per second. There are no loops or automatic retries.

The safe state after a failure is **no further command dispatch**. No electrical rollback or shutdown command is inferred. A matching ESP32 response reports the device operation result; a write acknowledgment does not verify the register's later value. A command timeout has an unknown hardware outcome. The bridge blocks further live sequences and writes until the active operator reviews the device and calls `/sequence-executions/:id/recover`. Interrupted live executions also require recovery after restart. Simulation never uses the UDP command transport or hardware recording.

Sequence definitions, immutable execution snapshots, and ordered events are stored in the existing private recording database. Live execution starts a linked run, and the execution stores its recording session ID, which can span run segments. The browser is not involved in scheduling. `/events` emits sequence events and active status; clients should reload the execution and paginated events after reconnecting.

## Run history (Batch 5D)

Every execution creates a durable sequence run before its first block. The execution stores the exact definition revision, mode, operator, start and end times, final state, completed step count, and a direct telemetry run ID for live mode. Simulations remain in sequence history without creating a hardware telemetry recording. The Runs and Sequences pages show the saved execution timeline to viewers without rerunning it. Step events include bounded telemetry snapshots; condition and branch events preserve comparison operands, evaluated values, packet sequence, and receive time. Command results and errors retain acknowledgment evidence and failure explanations.

`POST /sequences/:id/execute` accepts an optional client-generated UUID `execution_id`. Repeating the same request ID for the same operator, definition revision, and mode returns its existing execution instead of dispatching again. A bridge restart closes any unfinished execution as failed with `bridge_restart` and appends one recovery event. An interrupted live execution still requires device review before another write.
