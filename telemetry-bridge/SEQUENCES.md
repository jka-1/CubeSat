# Backend sequence execution (Batch 5B)

Sequences are version 1 JSON definitions with ordered `steps`. Supported blocks are `command`, `registerRead`, `registerWrite`, `delay`, `waitUntil`, and `if` with `then` and optional `else` arrays. An empty remaining step list terminates successfully. Conditions use `==`, `!=`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, and `NOT`. A metric operand is `{ "metric": "pv.busVoltageV" }`; a constant is `{ "constant": 5, "unit": "V" }`. Unknown telemetry stays unknown under `NOT` and cannot select a branch.

`POST /sequences` saves a definition; `PUT /sequences/:id` requires the current `revision`. `POST /sequences/:id/preflight` returns a 30-second confirmation token for a specific operator, revision, and device. `POST /sequences/:id/execute` accepts `{ "mode": "live", "confirmation_token": "..." }` or `{ "mode": "simulation", "telemetry": { ... } }`. Execution status and ordered events are available under `/sequence-executions` and `/sequence-executions/:id/events?after=0`. Active operator controls are `pause`, `resume`, and `stop` POST subroutes. Live start and resume require the command token as well as the authenticated operator session and CSRF header.

Live execution uses one server process and one active sequence lock. It requires fresh UDP telemetry from the pinned device and endpoint, a healthy recorder, and continuous operator lease ownership. Manual commands remain serialized against live sequence control. A branch attaches transactionally to an active recording for the same device and source address. It cannot stop or reset that recording on completion or failure. A branch started independently still creates and closes its own recording session; duplicate recording starts are rejected. Operators can stop a shared recording explicitly, while a sequence-owned recording remains protected until execution ends. The engine does not renew the operator lease; if browser heartbeats stop, the lease expires and execution fails. A pause waits for any transmitted command response, and time spent paused counts against the 30-minute run deadline. Pause expires after 60 seconds. Blocks are limited to 200, nesting to 8, delay and condition waits to 10 minutes, and live command dispatch to at most once per second. There are no loops or automatic retries.

The safe state after a failure is **no further command dispatch**. No electrical rollback or shutdown command is inferred. A matching ESP32 response reports the device operation result; a write acknowledgment does not verify the register's later value. A command timeout has an unknown hardware outcome. The bridge blocks further live sequences and writes until the active operator reviews the device and calls `/sequence-executions/:id/recover`. Interrupted live executions also require recovery after restart. Simulation never uses the UDP command transport or hardware recording.

Sequence definitions, immutable execution snapshots, and ordered events are stored in the existing private recording database. Live execution joins the current run or creates one if none is active. The execution stores both its initial recording run ID and recording session ID, which can span the existing telemetry-driven run segments. Branch state, comparison, command, and step events also appear as existing `sequence_step` events in the current session timeline; simulation never annotates hardware recordings. The browser is not involved in scheduling. `/events` emits sequence events and active status; clients should reload the execution and paginated events after reconnecting.

## Run history (Batch 5D)

Every execution creates a durable sequence run before its first block. The execution stores the exact definition revision, mode, operator, start and end times, final state, completed step count, and a direct telemetry run ID for live mode. Simulations remain in sequence history without creating a hardware telemetry recording. The Runs and Sequences pages show the saved execution timeline to operators without rerunning it. Viewer run timelines retain recorded branch annotations, while sequence definitions and their APIs remain operator-only. Step events include bounded telemetry snapshots; condition and branch events preserve comparison operands, evaluated values, packet sequence, and receive time. Command results and errors retain acknowledgment evidence and failure explanations.

`POST /sequences/:id/execute` accepts an optional client-generated UUID `execution_id`. Repeating the same request ID for the same operator, definition revision, and mode returns its existing execution instead of dispatching again. A bridge restart closes any unfinished execution as failed with `bridge_restart` and appends one recovery event. An interrupted live execution still requires device review before another write.

## Block-result operands and bit masks (Branch Definition)

A condition operand may be `{ "step": "<registerRead block id>" }`. It evaluates to the integer value that block read in the current execution, decoded with the register's byte order, and has type `hex`. The block must be a `registerRead` (or `i2c_read` command) that appears earlier on the same path; reads inside a sibling IF branch are not visible after that IF. Validation rejects other references. The comparison operator `&` (hex only) is TRUE when `(left & right) != 0`. Each read records a `register_value` event. In simulation, read values come from `telemetry.registers` keyed `"<addr>:<reg>"` (for example `{"0x40:0x00": 16679}`). No firmware change is required: the bridge reuses the `i2c_read` reply.

## User-added condition registers

A sequence may carry an optional top-level `registers` array (max 32) of registers added from the editor's condition picker:

```json
"registers": [{ "id": "user-48-00-2", "label": "Temp sensor", "addr": "0x48", "reg": "0x00", "len": 2, "endian": "big" }]
```

`id` is `user-<addr>-<reg>-<len>` (hex without `0x`). `addr` must be a 7-bit address `0x08`–`0x77`, `reg` `0x00`–`0xFF`, `len` 1 or 2, `endian` `big` or `little`, and `label` is optional (≤60 chars). Duplicate ids or duplicate addr/reg/len targets are rejected. A condition operand `{ "register": "user-48-00-2" }` has type `hex`. In live runs the engine issues an `i2c_read` for each referenced added register at condition-evaluation time (same paced path and events as catalog register operands: `command_intent`, `command_result`, and `command_error` on failure) and decodes it with the given byte order. In simulation the value comes from `telemetry.packet.register_values` keyed by the id or by `"<addr>:<reg>"`. The editor also remembers added registers in browser `localStorage` (`cubesat.sequence.registers.v1`) so they are offered for future definitions; that list is per browser, not shared through the bridge.
